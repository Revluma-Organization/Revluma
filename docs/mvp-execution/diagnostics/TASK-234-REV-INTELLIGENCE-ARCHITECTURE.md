## Request-to-response trace revalidated in source

1. **Browser:** `Frontend/Dashboard/src/lib/revStream.ts` posts the merchant message and conversation/finding identifiers to the authenticated Node gateway at `/api/v1/rev/stream`; browser code does not contact Python directly. The stream parser accepts only a complete final envelope and does not render partial provider payloads as a success.
2. **Node identity, acceptance and context:** `Backend/src/route/revRoute.js` applies authentication and the chat rate limiter. `revController.chatStream` resolves the authenticated organization, validates the message/finding, accepts the turn idempotently, verifies conversation ownership, and persists the accepted user turn. It builds bounded merchant context and loads the selected conversation's summary/context window under organization scope.
3. **Node → Python:** `Backend/src/services/mlService.js::streamInvestigation` posts to Python `/rev/stream` with the internal caller key, contract version, correlation/execution ID, a bounded execution deadline, and server-derived context. Ordinary JSON chat calls `/rev/investigate` through `mlService.investigate`; image-bearing JSON chat retains the separate `/orchestrate` compatibility path. The browser never supplies authoritative tenant identity, provider credentials or store evidence.
4. **Python routing and gate:** `python/src/serving/api.py` checks the internal caller and contract version. The streaming endpoint delegates to `src.agents.investigation.stream_investigation` / `run_investigation`. Python loads bounded conversation state/history, resolves store metadata, then `route_message` applies deterministic guards and intent understanding before evidence tools or specialists can run. Non-store intents return through `_conversation_result`; store intents proceed through the evidence/retrieval/orchestration path.
5. **Investigation:** for an eligible store-specific question, `python/src/intelligence/question_orchestration.py` builds a bounded, tenant-scoped plan; allowlisted read-only tools retrieve existing evidence; selected specialists calculate over that evidence; reconciliation, evidence/claim/outcome and narrative guardrails validate the result. Tool/specialist failure is represented as a bounded failure/partial outcome rather than an invented metric. Recommendations remain proposals; no Shopify mutation is dispatched.
6. **Response, persistence and stream:** Python validates evidence and response guardrails before emitting the final result. Node validates the independent investigation contract, writes the Rev turn and bounded context window, then emits `final`. The same persisted response is returned by the organization-scoped `GET /api/v1/rev/conversation/:id`, ordered by `sequence_number`; the Dashboard rehydrates URL-selected threads from that endpoint and renders persisted structured content through its normalizers. The code/tests establish the scoped path, not authenticated production restoration in this run.

## The “What is Shopify?” incident: what source proves and what it cannot

Before this change, `route_message` sent this wording to the model understanding layer unless another deterministic rule happened to match. The understanding prompt correctly says definitions/general knowledge must set `requires_store_data=false`, and `_safe_fallback` also recognizes “what is” as knowledge. However, the code had no deterministic route for this clear, context-free definition; a model classification with `requires_store_data=true` could therefore open the investigation gate. This is a confirmed routing weakness, **not evidence that it caused the reported production turn**.

If the turn routed to knowledge, `compose_knowledge` made a deep-role provider call. A provider exception was converted to a temporary-unavailable sentence, and `_dynamic_knowledge` then rendered its own safe explanation-unavailable message. The API envelope still marked that conversational result `success: true`; therefore a provider outage could appear as a completed but unhelpful chat turn. That is a confirmed failure-surface behavior, but the exact provider, model, status and whether it occurred for the reported question are unknown.

Before this patch, the Anthropic gateway path did not normalize SDK failures into the safe provider error contract or log provider/model/status/category/latency with the request correlation ID. Gemini already logged provider/model/role/status, but its provider events did not include the investigation correlation ID. Model-ID constants in `understanding.py` and `responder.py` were also misleading: the gateway actually selected `fast`/`deep` roles, and the responder constants only served as those role selectors. No available evidence establishes a bad production model ID, missing key, quota, timeout, outage or provider configuration error; do not attribute the incident to any of these without its request/log evidence.

The implementation adds a deterministic route for a context-free definition only when no store-reference phrase or store metric intent matched; “What is my revenue?” remains on the store-data route. Provider roles are now named roles, concrete Anthropic model IDs can be configured through `ANTHROPIC_FAST_MODEL` / `ANTHROPIC_DEEP_MODEL` (existing defaults retained), and Anthropic errors are normalized to bounded categories and logged with provider/model/role/status/category/latency/correlation ID. Provider prompts, API keys and raw exception text are not logged, and no cross-provider fallback was added. These changes make a new occurrence diagnosable and close the confirmed routing gap; they cannot reconstruct the cause of an earlier occurrence.

## General knowledge versus Shopify data

The runtime test added for “What is Shopify?” proves that this explicit general definition takes the `deterministic_knowledge` route, bypasses the intent model, executes no Shopify evidence tool or specialist, returns empty evidence, and does not inherit a previous revenue investigation. A metric-definition question such as “What is my revenue?” still routes to revenue tools. The shared request path still performs bounded conversation/store-context and memory reads for routing and continuity; these are not domain evidence investigations. No general knowledge answer is presented as a fact about the merchant's store.
