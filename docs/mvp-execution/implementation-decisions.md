## REV-DEC-0012 — Task 198 merchant-calendar reporting periods and currency-honest revenue
2026-11-07. Reporting periods resolve on the merchant's IANA calendar (store settings > `store_profiles.iana_timezone` > UTC; conflicting stores → UTC + explicit warning), with DST-safe half-open `[start, end)` windows. "this week"/"last week" are ISO calendar weeks (Monday-start) in the merchant timezone; "last month"/"this month" are calendar months; explicit date ranges are local-midnight half-open windows. Comparison windows are the previous calendar unit for full calendar windows and the equal-length immediately-preceding period for rolling/partial windows. Revenue is retrieved and displayed per verified ISO currency; incompatible currencies are never summed (the refusal is explicit in Python revenue evidence, business state, and the Node revenue resource), and no display layer assumes USD. Consequences: (1) "this week" semantics change from a rolling 7×24h window to the local calendar week to now — comparison of the partial week uses the equal-length immediately-preceding period, and the prior full week remains available as "last week"; (2) multi-currency organizations lose scalar business-state revenue (replaced by per-currency evidence) — an intentional fail-closed trade; (3) a revenue zero is asserted as `"0.00"` in the verified currency only with complete certified coverage, otherwise the item is demoted, never a count zero. Alternatives rejected: fixed 7×24h/30×24h windows (DST drift, wrong merchant calendar), summing across currencies (fabricated totals), assuming a default currency (mislabelled money). Related: TASK 198; rev-evidence-v2 contract; REV-DEC-0009 (typed identity, same fail-closed philosophy).

## REV-DEC-0015 — Task 204 reasoning epistemics: one claim contract, four earned grades, fail-closed at the boundary
2026-11-07. A number in a merchant-facing answer must be a *recorded claim* with an epistemic grade that is *earned from the evidence* — never a label the model decides to print. Decisions: (1) **One contract, four grades** — `rev-claim-v1` reuses the evidence contract's existing `CLAIM_GRADES` (`verified_fact` / `calculated_observation` / `hypothesis` / `unknown`) so the machine word and the merchant word are the same word; no new taxonomy. (2) **Grades are earned, not assigned** — `verified_fact` cites only available evidence and carries the item's own value/currency; `calculated_observation` must list `calculation_inputs` (a subset of cited items) from which its money value is re-derivable within rounding; a `hypothesis` must carry `candidate_causes` and **may not carry a numeric value** (a hypothesis with a number is a defect, not a grade); an `unknown` may carry no value and states its `limitation`. (3) **Fabrication is a validation error, not a rounding courtesy** — false precision (money >2dp, percent >1dp), an asserted impact without a calculation method, an unknown carrying a value, a claim citing unknown/foreign (cross-tenant or cross-store) evidence, and a restated claim without `source_investigation` all produce stable machine-readable error codes and fail the whole response at the Node boundary (400); the Python pipeline validates before recording, so an unearned number is replaced by an `unknown` claim plus a visible warning rather than emitted. (4) **Restated claims are the only claims that skip re-derivation** — provenance and corrections restatement must not re-validate a previously earned value against *current* evidence (that would manufacture spurious "unknown evidence" failures); a restated claim preserves grade, value and `claim_id` verbatim and is shape-validated with `source_investigation`; `can_promote` forbids upgrading a restated or corrected claim. (5) **The merchant's assertion is not a source** — a correction records the original claim as `superseded` (id preserved, pair verifiable across the boundary) and the correction itself as `unknown` ("invalidated pending re-verification"), never re-graded to a fact from the merchant's word; the merchant memory is invalidated in the same step so the figure cannot seed future follow-ups. (6) **Provenance answers from the record, before the chat router** — "where did that figure come from?" is routed from `last_claims` (≤10, well-formed-only, tenant-filtered) *before* conversational early-returns, restates the claim with its grade, gives the source and a human-readable retrieval time (raw ISO timestamps never appear in merchant text), and refuses to re-estimate. (7) **The follow-up record survives both boundaries** — `last_claims` + the allowlisted `checkout_query` drill-down are persisted in the bounded context (write- and read-time filtering, defense in depth) and carried through the Node controller into both the SSE `final` payload and persisted content, so a follow-up inherits scope ("what about those?" stays abandoned-only) and streamed and stored answers agree. (8) **One contract enforced twice, one golden** — Python keystone (`intelligence/epistemics.py`) + Node mirror (`services/revEpistemics.js`, raw-string currency/percent regexes, no `Number()` normalization) with parity locked by a Python-generated golden fixture (`gen_epistemic_golden.py` → `revEpistemics.golden.json`), the Task 203 pattern. Alternatives rejected: a fifth "correction" grade (a correction is a supersession pair, not a new epistemic state); re-deriving restated claims against current evidence (spurious failures); trusting the model's in-answer grade labels (the defect this task removes); a separate comparison-claim class (comparison data rides on `period.comparison_window` of the same claim). Related: TASK 204 (consolidates 212–216); rev-evidence-v2 contract (CLAIM_GRADES); REV-DEC-0012/0013 (fail-closed philosophy); Task 203 (quality model, golden-parity pattern).

## REV-DEC-0018 — Task 206 revenue/checkout/priority investigation: computed comparisons, contributions and rankings from recorded windows only
2026-11-07. Three question families (revenue drop, checkout abandonment, "what should I fix first") are answered from the recorded evidence windows with three distinct, named computations — and each is refused, never invented, when its inputs are not recorded. Decisions: (1) **A decline is a change, not a cause** — revenue/checkout/product answers compare the resolved reporting window with the resolved comparison window (the single source of truth from `resolve_reporting_period`; retrieval never invents its own period); "worse" requires the equal-elapsed or prior-calendar comparable period, fully preceding the reporting window; zero/empty previous windows are named unavailable states, never a fabricated baseline or percentage. (2) **A product's role is a contribution, not a cause** — product comparison reuses the Task 202 line-item retrieval over both windows (`product_recorded_value_change`, top 10 by |delta|, percent only when previous > 0, evidence ids on both sides) and the revenue value change is decomposed into the two recorded drivers (`value-decomposition-v1`: count_effect = Δcount × aov_prev; value_effect = residual, so the effects sum exactly to the recorded change; driver named volume-driven/value-driven/mixed-offsetting/equally-split/no_change from the recorded effects) — the text says "contributed", never "caused". (3) **A priority is a ranking with named exclusions** — `finding-priority-v1` ranks only open/acknowledged findings whose recorded evidence is currently verified; recorded severity > freshness > stable id; every exclusion carries a machine-readable reason (`historical`, `evidence_unverified`, `evidence_unavailable`, `stale_findings_require_reverification`, …) and `no_valid_findings` is a first-class state (verified-healthy vs stale vs unavailable are different sentences); ties are surfaced, never broken silently. (4) **Change is stated, not hidden** — the bounded context persists `last_priority`; when the top changes between conversations the response carries `priority_change` (reason: excluded / re-ranked lower / no longer in the recorded set) and says "How this differs from what I told you before" — an invalidated top is never silently re-presented. ## REV-DEC-0019 — Task 210 adaptive answer structure and confidence communication: structure earned from the question, confidence earned from the evidence, no number ever fabricated
2026-11-07. The response shape and the confidence standing stop being fixed outputs and become earned inputs: a deterministic keystone (`intelligence/response_adaptation.py`, pure functions) classifies the response profile (intents A–H, complexity, explanation depth) from the existing routing output and selects the ordered composable elements from a closed vocabulary — the LLM never picks structure (spec 2), a direct factual question gets `[direct_answer, evidence, confidence]`, not four slots (spec 4), and degraded paths emit only the earned elements plus a suggested investigation. Confidence is per-claim, computed by documented method D1 (grade gate: hypothesis ≤ limited, unknown = insufficient; worst sufficiency across the claim's cited items; named penalties for conflicting/stale/partial/non-comparable-currency evidence; floor high for fully-verified in-window facts), reported as four categories with machine-readable reasons and communicated as natural-language sentences — never a score, never a percentage, and coverage (how much was seen) is a separate report, never a confidence input (spec 5.D, 6). The `response` contract gains ordered non-empty `sections`, restructured `confidence` `{category, claims, coverage, communication}`, and top-level `response_profile`; the legacy four keys stay populated for existing consumers while the fabricated numeric `score` leaves new investigation responses (legacy `{score, basis}` retained only for persisted legacy turns via the frontend adapter). Node re-derives every category at the boundary (`revResponseAdaptation.js`, same D1, fail-closed: no numeric score, no unknown category, no disagreement with re-derivation, no coverage/confidence conflation, no `%` in communication, closed section vocabulary, no duplicates) and a Python-generated golden set pins Python↔Node identity (Task 203/204/207/208 pattern). The frontend renders `sections` in backend order when present (legacy 4-key derivation not re-run), renders the standing only as the backend's natural-language sentence (ordered confidence section, else one deduplicated paragraph — no badge/pill/uppercase, per the spec §5 badge discipline), and renders coverage separately under "How I checked" as "Coverage and data state"; malformed confidence is fail-hidden. ## REV-DEC-0033 — Task 224 the Rev Intelligence error, retry, handoff and accessibility experience is made truthful, recoverable and announced
2026-11-07. Task 224 (original Tasks 305–311) productionizes the Rev Intelligence workspace's error, retry, context-handoff, responsive, keyboard and announcement behavior, **frontend-only** (layered on latest main `3a3baa0`, including Tasks 223, 225 **and 226** — this work was authored before Task 226 and re-reconciled onto it, so it composes Task 226's unified workspace language rather than a parallel one) — no backend source, data model, migration, or read-only/security boundary changed. Decisions: (1) **Two layers that cannot drift: a closed recovery *decision* and the shared *wording*** — `src/lib/revError.ts` (`classifyRevFailure`, `classifyRevResponseError`, `isAssertiveRevFailure`) is the single **decision** layer: it maps every failure the conversation can observe (a structured backend code, or a raw HTTP/transport status via the reused Task-220 `classifyCommandCenterFailure`) to `{ kind, retryable, retryAfterSeconds }` and, for `isAssertiveRevFailure`, whether the transition is urgent. It owns **no message text**: the merchant-facing wording is the single source of truth in `cleanError()`, which (post Task 226) delegates to the shared `explainWorkspaceError`/`merchantMessage` workspace language plus a small `revSpecific` override table for the few Rev-specific codes. This is the explicit reconciliation with Task 226 (REV-DEC-0032): before Task 226 this task's classifier owned both the decision and the strings; Task 226's "unify workspace language" made the shared classifier authoritative for wording, so this task deliberately gave its classifier up its message strings and now supplies only the recovery decision that wording does not decide (raw HTTP statuses still surface *distinct* truthful messages — 404→not-found, 429→rate-limited, 502/503/504→unavailable — because the `cleanError` reason is normalised to a numeric status, and the long-standing `"Rev is taking a moment…"` closed fallback is retained for a plain transport error with no code and no status; no backend/provider/SQL/credential text is ever interpolated). (2) **Recovery is offered only where it is honest** — the retry control is shown for a transient failure (429/5xx/timeout/network/malformed) or a finding rejection (recover-in-place: fix the finding, re-send); it is withheld for permanent `401/403/422` where re-sending the identical request is futile (a 401/403 still announces through the assertive path). (3) **`Retry-After` is respected, never auto-retried** — `RetryAfterButton` renders a live countdown ("Retry in Ns") and is `disabled` until the server's `Retry-After` window elapses, then re-enables exactly on expiry; `api.ts` already copies the header onto `ApiError.retryAfter`, read end-to-end by the classifier. A pure-integer `Retry-After` is strictly a delta-seconds and a negative one is rejected (`null`), never parsed as a date that yields "retry in 0s". There is no auto-retry loop anywhere; `handleRetry` only prepares the retry (draft + input) and the merchant confirms, and a recovered pre-save rejection re-sends the existing `questionRef` so nothing is duplicated. (4) **No fabricated success on a failed turn** — every failure renders a real `rev-error` message; nothing shows "done"/"saved"/"resolved". (5) **Context handoff is explicit and escapable** — the Task-211 finding-handoff surface (deep link, revalidation-before-current-advice caveat, pre-filled editable draft that does not auto-send, `findingId` carried into the first turn) is reused; a new "Start a separate conversation" control (307.17) in the finding banner clears the inherited context and resets to the base route, and the resulting turn sends no `findingId`, so an independent investigation is a deliberate act and the first response always addresses the finding when one is carried (Task 225's finding→Rev and conversation→Command-Center navigation is left intact). (6) **Announcements are a single canonical live region** — one `aria-live` region (`data-testid="rev-status-region"`), **polite** normally and **assertive** only for `isAssertiveRevFailure` kinds (5xx/429/timeout/network/invalid-contract/401/403), rendered only while the workspace owns focus (removed behind a modal — a background live region must not announce behind a modal, and no required transition fires during a modal interaction so none is dropped). It announces each transition once — loading, context handoff, recovery, submission, acceptance, completion, retry — never re-announcing the whole conversation. (7) **Responsive is a structural invariant** — the workspace root is `overflow-hidden` (no horizontal page scroll 320–1920), the message stream is its own `overflow-y-auto` region separate from the fixed composer, the history trigger is a labelled `aria-expanded` hamburger, and the open history drawer is a `role="dialog" aria-modal="true"` surface on a `z-[170]` overlay that stacks above the workspace; the viewport matrix is a documented manual production-acceptance check (jsdom does not do real layout). (8) **The 305/306 assertions respect Task 223's draft-preserving submission** — Task 223 clears the input only once the server persists, so after a pre-persistence failure the question is in both the preserved input and the user bubble; the assertions count the user-message bubble only (`threadQuestionCount`) so they verify "preserved in the thread / not duplicated in the thread" without being fooled by the preserved input. Alternatives rejected: a classifier that also owned the message strings (drifted from Task 226's unified language after the merge — the root cause this re-reconciliation removes); per-component ad-hoc error strings (drift, no single retry policy); an unconditional "Try again" (a futile retry on a permanent 401/403/422 and no backoff on 429/5xx); an auto-retry (rate-limit loops, hammering a dead endpoint); interpolating the server's `message` (internal detail leakage); an always-mounted `aria-live` region (defeats the modal's `aria-modal` scoping); and hiding context rather than offering an explicit independent path (the merchant could not deliberately escape the inherited finding).
