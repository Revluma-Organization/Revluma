# Task 233 — implementation record (in progress; not release-ready)

The reaper conditionally fails a resource only if its observed status, attempt/check/update timestamps, store and domain still match; errors propagate and a strict ledger re-read is used. It retains checkpoint and record counts. Store terminalization now conditionally matches the observed status, lifecycle, job ID and update timestamp, avoiding clearing a replacement job based on an obsolete store scan.

These are metadata compare-and-swap guards, not worker leases, transactional page checkpoints, fencing of business writes, or an atomic aggregate ledger transition. Existing timestamps have microsecond database precision but JavaScript Date has millisecond precision; exact equality on a row written with sub-millisecond precision may cause a safe no-op, so liveness requires further design and validation. Resource changes concurrent with aggregate derivation remain a risk. No migration was added. Do not deploy these partial changes as the finished task.

Required work remains: recoverable per-resource pages with atomic checkpoint/write boundaries and idempotency; renewable bounded ownership and write fencing; scope-aware revocation/uninstall/reauthorization; graceful Node/Python drain/restart; classified bounded retries and uncertain-commit reconciliation; AI timeout/recovery; truthful propagation and privacy-safe evidence; Task 232 compatibility and all acceptance tests. Keep unrelated incomplete Task 231 changes separate from any eventual release.
