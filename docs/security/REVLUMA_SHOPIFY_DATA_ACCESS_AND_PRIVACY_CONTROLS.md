# Shopify access and privacy controls — working audit

2026-11-05. This is not privacy certification. Read-only Supabase metadata observations on `Revluma-Database`: RLS enabled for stores, customers, orders, order_items, abandoned_carts, abandoned_cart_items, webhook_deliveries, conversations, conversation_messages and intelligence_findings. `pg_policies` showed policies for stores, customers, orders, abandoned_carts, abandoned_cart_items and conversations/messages; none for order_items, webhook_deliveries or intelligence_findings. No direct `information_schema.role_table_grants` rows for anon/authenticated/public on these ten tables were returned. This does not prove effective privileges (role inheritance, owner/service bypass, functions and application access require independent checks) or cross-tenant isolation. Public security-definer functions observed: `rev_is_org_member` (search_path pg_catalog, public), `rls_auto_enable` (pg_catalog), both postgres-owned. Review EXECUTE grants and bodies, then test concurrent real tenant contexts; metadata is not a negative-access test.

`Backend/src/utils/encryption.js`: tokens are encrypted with AES-256-CBC using a configured key and random IV. CBC is not authenticated encryption; design a versioned authenticated-encryption migration with key rotation and legacy read support before modification. Never log tokens or key values. Production key availability, storage controls, and real-token validity remain unverified.

`Backend/src/utils/shopify.js` forces `write_discounts`; `Backend/src/services/recoveryActionService.js` contains Shopify discount creation, so removing the scope without reviewing legacy functionality and merchant consent could break flows. This conflicts with the target read-only MVP: audit active routes, workers, feature gates and existing subscriptions; propose a staged removal with reauthorization and rollback. No scope has been changed.

Shopify requires public-app compliance endpoints for `customers/data_request`, `customers/redact`, and `shop/redact`, 2xx acknowledgment of receipt and completion within the documented window, subject to legal retention exceptions: [Shopify privacy requirements](https://shopify.dev/docs/apps/build/compliance/privacy-law-compliance). Current draft rejects these topics rather than falsely claim processing, but has **no durable compliance queue or complete request/erasure workflow** and therefore is not a compliant implementation. Live subscription and delivery status are unknown. Full implementation needs verified identity, after-uninstall handling, securely persisted request, cross-table data inventory, legal-retention policy, scoped transactional execution, completion audit, recovery and idempotency tests. Do not deploy or claim compliant until designed, tested and operationally verified. Never delete live merchant data to test.

Webhook duplicate handling now distinguishes `processed` from `received`, scopes a duplicate/retry to its store/topic, and never acknowledges an in-flight delivery as completed. A process crash can leave `received` indefinitely: **durable lease/recovery is still required**, and bounded Shopify retries are not a permanent queue. Live verification and real cross-tenant tests remain outstanding.
